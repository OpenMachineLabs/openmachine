# Motion grammar

These are design hypotheses distilled from indexed sources, not measured claims
about audience comprehension. Retrieve concrete cases by source ID and evaluate
the resulting video with its actual audience.

## A promise the mechanism can prove

Begin with an observable problem, unexpected result or precise question. Move to
one example. A project overview can explain one representative workflow and name
the broader scope at the end. Listing every feature rarely explains one.

| Need | Structure | Avoid |
|---|---|---|
| Project introduction | Friction → workflow → visible result → next step | Feature inventory |
| Module explanation | Input → internal state → decision → output → boundary | Directory tree as architecture |
| Article teaser | Question → partial explanation → insight → article | Paragraphs on every frame |
| Architecture change | Same initial condition → changed mechanism → difference | Unequal before/after scenarios |
| Failure explanation | Expected path → failure → retained state → recovery | Failed work disappearing without consequence |

Spend most of the time on the mechanism. A starting budget is 4 seconds for the
question, 20–30 for a worked example and 6–10 for result/boundary. These are our
adjustable production defaults, not timing observations from a reference.

## Motion is a factual statement

| Visual action | Implied statement | Check |
|---|---|---|
| Object follows a connector | Information/work follows that relationship | Direction and payload are supported |
| Object splits | Something was duplicated/dispatched | State exactly what is copied |
| Branches move together | Work overlaps | Concurrency exists; durations are illustrative |
| Branches meet | A join depends on those inputs | Output waits for required inputs |
| One branch highlighted | This example selects one alternative | Router does not activate every branch |
| Object expands | Identity persists while state/detail changes | Keep ID, label and visual anchor |
| Check mark | Defined completion condition was met | Attempted work is not success |
| Loop repeats | Output affects another attempt | Preserve stop/failure conditions |
| One path is faster | Performance differs | Require measurement or remove comparison |

Do not decorate unrelated concepts with causal arrows. Use progress bars,
percentages and clocks only for defined quantities. An illustrative sequence
must not imply a latency benchmark.

## Preserve identity and reveal relevant state

Keep a request, document or artifact recognizable. Introduce an input, expose a
transformation, hold its output, then add the next relationship. Abstraction helps
when it removes irrelevant detail; it misleads when it removes the reason for the
result. A literal UI demo requires observed UI evidence, not invented screenshots
with a real product's name.

Routing shows quiet alternatives then one active path. Parallel work reveals
concurrent branches and a waiting join. Feedback reveals an evaluation consequence
and a bounded revision, without promising endless improvement. Comparison keeps
initial conditions and scales matched.

## Let the viewer read

Use one primary sentence and one visual explanation per scene. Hold the result
after movement finishes. Character limits are guardrails: unfamiliar terminology,
language and mobile playback may need less text or more time. Explain technical
names through relationships. Put precise references in the evidence packet.

## When a custom scene is needed

- **Persistent state:** separate the store from messages that update it.
- **Retries/cancellation:** separate attempts, retained receipts and final results.
- **Streaming:** append to the same output object instead of replacing it.
- **Caching:** distinguish lookup, hit/miss and reuse; do not invent hit rates.
- **Performance:** use real axes, units, conditions and sourced measurements.
- **Interactive references:** select a scenario and counterfactual; use holds to
  compensate for the viewer's inability to change inputs.

Hold a clear composition when motion adds no information. Avoid idle orbiting
nodes, decorative particles and camera moves that reset the mental model.
Surprise should come from a revealed mechanism.
